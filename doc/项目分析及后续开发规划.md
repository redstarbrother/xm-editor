# XmEditor 项目现状分析与后续优化路线图

> 分析日期：2026-08-26  
> 分析对象：`@putanut/xm-editor` 0.1.6  
> 当前分支：`feature/new-ai`  
> 分析范围：项目架构、核心实现、扩展体系、构建发布、测试与工程化、同类开源项目能力对照

## 1. 总体结论

XmEditor 已经不是简单的富文本编辑器 Demo，而是一个具备完整产品轮廓的 Vue 3 + Tiptap 编辑器组件库。项目已经实现扩展体系、三套 Preset、Slash Menu、Bubble Menu、Fixed Menu、表格、目录、拖拽、图片上传和代码块等主要能力，具备继续产品化的基础。

目前项目仍处于“功能开发较快、工程化基础偏弱”的 0.x 阶段：

| 维度 | 当前评价 | 说明 |
| --- | --- | --- |
| 产品完整度 | 中等 | 核心编辑功能已成形，高级内容块、协同和审阅能力仍缺失 |
| 架构可扩展性 | 较好 | Extension Manifest 和 Preset 的方向正确 |
| 工程成熟度 | 偏低 | 缺少类型、测试、代码质量和发布验证体系 |
| 性能与包体积 | 需要重点治理 | 基础产物体积较大，按需加载能力不足 |
| 生产可用性 | 中低 | 生命周期、配置隔离和多实例行为仍存在风险 |

下一阶段建议先完成一次“质量与架构收口”，再扩展协同、评论和 AI 等高级功能。当前不宜继续单纯增加按钮或 Extension 数量。

## 2. 项目定位与技术架构

### 2.1 项目定位

XmEditor 当前适合定位为：

> Vue 生态中轻量、可组装、中文体验完善、业务接入成本低的 Tiptap 编辑器套件。

相较于直接封装 Tiptap，XmEditor 的核心价值在于：

- 提供可直接使用的编辑器产品形态，而不只是编辑内核。
- 用统一的 Extension Manifest 描述编辑逻辑和菜单 UI。
- 通过 Preset 适配文档、CMS、评论框等不同场景。
- 提供表格、目录、拖拽、代码块等需要较多交互开发的高级能力。

### 2.2 核心模块

| 模块 | 主要职责 |
| --- | --- |
| `src/core/XmEditor.js` | 解析配置、创建 Tiptap Editor、动态挂载 Vue UI、创建代理 API |
| `src/core/ExtensionManager.js` | 收集 Tiptap Extension、菜单 Manifest 和 UI 组件 |
| `src/core/XmEditorView.vue` | 渲染编辑区域、菜单、目录、拖拽手柄和表格辅助 UI |
| `src/core/proxyEditor.js` | 封装内容、光标、字体、行高和目录等外部 API |
| `src/utils/extensionUtil.js` | 规范自定义 Extension 的结构和配置方法 |
| `src/utils/presetUtil.js` | 合并 Preset 默认配置和用户覆盖配置 |
| `src/presets/*` | 提供 NotionLike、Basic 和 Comment 三种产品形态 |

### 2.3 主要数据流

```mermaid
flowchart LR
  A[用户配置或 Preset] --> B[XmEditor]
  B --> C[配置规范化]
  C --> D[ExtensionManager]
  D --> E[Tiptap Extensions]
  D --> F[Menu Manifests]
  D --> G[Vue UI Components]
  E --> H[Tiptap / ProseMirror]
  F --> I[XmEditorView]
  G --> I
  H <--> I
  H --> J[Proxy API 与事件]
```

当前实际代码尚未形成独立的“配置规范化”模块，该步骤是后续推荐补充的关键架构层。

## 3. 当前已有优势

### 3.1 Extension-First 方向正确

`ExtensionManager` 能够统一收集：

- Tiptap Extension
- Fixed Menu 配置
- Bubble Menu 配置
- Slash Menu 配置
- Suggestion 配置
- Vue UI 组件
- TOC、DragHandle、Table 等特殊组件配置

这种结构优于将所有功能直接写进固定工具栏，扩展可以同时贡献编辑能力和 UI，并能够通过 Preset 组合。

### 3.2 已经形成多场景 Preset

项目提供三种预设：

- `NotionLike`：完整文档编辑体验。
- `Basic`：带固定工具栏的通用富文本编辑器。
- `Comment`：面向评论、聊天等轻量输入场景。

Preset 支持按照 Extension 名称进行覆盖，便于业务定制单个扩展，而无需重新声明全部扩展。

## 4. 当前主要问题与风险

## 4.1 P0：生命周期与实例清理不完整

`XmEditor` 内部通过 `createApp()` 动态创建 Vue App，但对外返回的是 Proxy。Proxy 中的 `destroy()` 只调用 `editor.destroy()`，没有调用 Vue App 的 `unmount()`。

可能产生的问题：

- Vue 组件和监听器没有完整清理。
- 多次创建、销毁编辑器后可能出现内存泄漏。
- 动态挂载的弹层或全局事件可能残留。
- `onUnmounted` 中注册的清理逻辑可能无法正常执行。

建议将 Vue App、Tiptap Editor、Suggestion Popup 和外部 DOM 节点统一交给一个 Runtime 管理，并保证 `destroy()` 幂等。

```js
destroy() {
  if (this.destroyed) return
  this.destroyed = true
  this.vueApp?.unmount()
  this.tiptapEditor?.destroy()
  this.element?.replaceChildren()
}
```

### 4.1.1 现状核查与问题边界

本节基于当前源码（`src/core/XmEditor.js`、`src/core/proxyEditor.js`、`src/extensions/Suggestion/*`、`src/extensions/Toc/*`、`src/extensions/Table/TableExtension.js` 及相关 Vue 组件）细化修复范围。

当前销毁链路如下：

```text
宿主调用 proxy.destroy()
  └─ editor.destroy()
       ├─ ProseMirror PluginView.destroy()（仅能清理部分插件资源）
       └─ Tiptap onDestroy 回调

Vue createApp() ──未保存 app 实例、未调用 app.unmount()──> Vue 组件树残留
```

已确认的资源和风险：

| 资源 | 创建位置 | 当前清理方式 | 风险 |
| --- | --- | --- | --- |
| 主 Vue App/组件树 | `XmEditor.mountUI()` | 无 `unmount()` | 组件监听器、`setInterval`、NodeView 关联引用可能残留 |
| Suggestion popup App、Tippy、浮层 DOM | `createSuggestionPopup()` | 仅在 `onExit()` 调用 | 编辑器异常销毁或插件未触发 `onExit` 时可能残留 |
| TOC 防抖定时器 | `tocUtils.debounce()` | 无取消接口 | 销毁后仍可能执行回调并访问已销毁 Editor |
| TOC 高亮 setup/RAF/scroll 监听 | `tocHighlight.js` | 清理 timer、监听器；未完整取消 RAF | 延迟回调可能在销毁后执行 |
| TOC Panel transaction 监听、轮询 | `TocPanel.vue` | `onUnmounted` 才清理 | 主 App 未卸载时不会触发清理 |
| Table 增删按钮 | `TableExtension.js` | PluginView.destroy() | 依赖 Tiptap destroy；没有统一资源登记 |
| 图片拖拽监听、RAF | `ImageView.vue` | `onUnmounted`/`stopResize()` | 依赖 NodeView 正确卸载；缺少统一兜底 |
| 宿主挂载 DOM | `app.mount(this.element)` | 未移除 | 无法区分编辑器节点与宿主已有节点 |

`themeLoader` 使用全局固定 ID 的代码主题链接属于 4.8 的多实例主题问题；本次不在 Runtime 中直接删除该节点，避免一个实例销毁时误删其他实例资源。后续应通过实例作用域或引用计数单独治理。

### 4.1.2 修复目标与不变量

修复完成后需要满足以下不变量：

1. 一个 `XmEditor` 实例拥有唯一 Runtime，所有由该实例创建的 App、Editor、弹层、定时器、监听器和外部节点都可追踪。
2. `destroy()` 可从 Class API、Proxy API、宿主 Vue `onBeforeUnmount` 以及异常回滚路径调用，并且幂等。
3. 销毁过程中任何单个清理器抛错都不能阻断后续清理；用户 `onDestroy` 最多触发一次。
4. 只移除 Runtime 自己创建的挂载节点和 Portal 节点，不清空宿主元素中其他业务节点，也不影响其他编辑器实例。
5. 销毁完成后，所有异步回调在执行前都能识别 Runtime 已进入 `destroying/destroyed` 状态并直接退出。
6. 现有公开 API 行为保持兼容；仅新增可选的状态查询/错误语义，不要求业务立即改写调用方式。

### 4.1.3 目标架构：EditorRuntime 资源管理器

新增 `src/core/EditorRuntime.js`，作为实例级生命周期控制器。建议接口：

```js
class EditorRuntime {
  state = 'created' // created | mounted | destroying | destroyed

  registerCleanup(cleanup, options = {}) {}
  trackNode(node, options = {}) {}
  setVueApp(app) {}
  setTiptapEditor(editor) {}
  isAlive() {}
  destroy(reason = 'manual') {}
}
```

实现要求：

- `registerCleanup` 返回取消注册函数；同一清理器只执行一次。
- 清理器按阶段登记并以逆序执行：`before-vue`（关闭弹层、取消异步任务）→ Vue `unmount` → Tiptap `destroy` → `after-editor`（移除 Portal/挂载节点）。
- `destroy()` 首次调用立即将状态设为 `destroying`，后续调用直接返回，防止用户回调重入。
- 每个清理器使用 `try/finally` 隔离异常，并记录 `label`；开发环境可汇总错误，生产环境不阻塞销毁。
- `trackNode` 只追踪 Runtime 创建的节点，销毁时调用 `remove()`，不使用 `host.replaceChildren()`。
- Runtime 不依赖 Vue 响应式，便于在无 DOM/SSR 检查和单元测试中复用。

推荐生命周期时序：

```text
new XmEditor()
  → 创建 Runtime
  → 创建唯一 mountEl 并挂载 Vue App
  → 创建 Tiptap Editor
  → Runtime.state = mounted

destroy()
  → CAS: mounted/created → destroying（重复调用立即返回）
  → before-vue 清理：popup、timer、RAF、外部订阅
  → vueApp.unmount()
  → tiptapEditor.destroy()
  → after-editor 清理：Portal、mountEl、引用和注册表
  → Runtime.state = destroyed
```

> 建议先卸载 Vue，再销毁 Tiptap：Vue 组件的 `onUnmounted` 清理逻辑仍可安全访问 Editor；随后由 Tiptap 触发 PluginView/Extension 的原生销毁钩子。

### 4.1.4 具体改动清单

#### A. `XmEditor` 保存并托管 App、挂载点和异常回滚

- 构造器最开始创建 `this.runtime = new EditorRuntime({ host: options.el })`。
- `mountUI()` 不再直接把 App 挂到宿主元素，而是创建 `mountEl`，登记到 Runtime 后执行 `app.mount(mountEl)`；保存 `this.vueApp = app` 和 `this.mountEl = mountEl`。
- `mountUI()` 返回 `{ app, vm, mountEl }` 或直接写入 Runtime，禁止只返回 Vue `vm`。
- 初始化过程使用 `try/catch`：任一扩展、Tiptap 或 Vue 挂载步骤失败时调用 Runtime 回滚已创建资源，再原样抛出初始化异常。
- `XmEditor.destroy()` 只委托 `this.runtime.destroy('api')`，不再直接调用 `tiptapEditor.destroy()`。
- 可增加只读 getter：`isDestroyed` 或 `getRuntimeState()`，供调试和测试使用。

#### B. `proxyEditor` 委托 Runtime，统一销毁语义

- `createEditorProxy(editor, runtime)` 新增 Runtime 参数。
- `proxy.destroy()` 改为 `runtime.destroy('proxy')`。
- `proxy.instance` 继续返回底层 Tiptap Editor；对于已销毁实例，内容读取/命令类方法统一抛出明确的 `EditorDestroyedError`（或保持兼容地返回空值，但必须文档化）。
- `getToc().onUpdate()` 返回取消订阅函数，并在 Runtime 销毁时清空剩余 listeners，避免用户回调被 storage 长期持有。

#### C. Suggestion Popup 纳入 Runtime

- `createSuggestionPopup(props, runtime)` 将 popup App、Tippy 实例和 `el` 全部登记到 Runtime 的 `before-vue`/`after-editor` 清理队列。
- `destroy()` 自身幂等：按 `tippy.destroy()` → `app.unmount()` → `el.remove()` 顺序执行，并解除 `popup`、`vm` 引用。
- `Suggestion.js` 的 `onExit()` 继续主动销毁；Runtime 销毁作为兜底，不能重复报错。
- `onUpdate`、`onKeyDown` 在 Runtime 非 alive 时直接返回，避免销毁后的异步事件访问组件实例。

#### D. TOC 防抖、高亮和 Panel 清理闭环

- 将 `debounce()` 改为返回带 `cancel()`/`flush()` 的函数；`TocExtension.onDestroy()` 调用 `debouncedUpdate.cancel()`。
- `createScrollHighlighter.cleanup()` 同时取消 `setupTimer` 和待执行 `requestAnimationFrame`，并把 `scrollHandler`、`scrollContainer`、当前状态置空。
- `update()`、`forceUpdate()` 在 Editor 已销毁或 Runtime 非 alive 时直接返回。
- `TocPanel.vue` 将 transaction handler、`storagePoller` 的声明和清理放在同一 `onBeforeUnmount`；不在 `onMounted` 内嵌套注册生命周期钩子。
- `getToc().onUpdate()`/`offUpdate()` 与组件卸载联动，确保 storage 中不保留已卸载组件回调。

#### E. 其他插件资源登记与组件卸载兜底

- 保留 `TableExtension` PluginView.destroy、图片 NodeView `onUnmounted` 等局部清理，同时为动态创建的 body 节点和 RAF 提供 Runtime 登记兜底。
- `TableExtension` 的 `rowBtn`/`colBtn` 在创建后调用 `runtime.trackNode()`；销毁时先解绑 `onclick` 再移除节点。
- 对 DragHandle、TableContextMenu、ImageView、CodeBlock 等组件，统一检查 `onMounted` 与 `onBeforeUnmount` 是否成对出现，避免把清理依赖放在 Tiptap 销毁之后。
- 所有跨实例 Portal 节点使用实例标识（如 `data-xm-runtime-id`），禁止按通用 class/固定 ID 批量删除。

#### F. 宿主 DOM 和公共 API 契约

- 为每个实例生成唯一 `runtimeId`，挂载结构建议为：`host → [data-xm-editor-mount="runtimeId"] → .xm-editor-root`。
- 销毁只移除该 `mountEl`；宿主元素的业务占位节点、兄弟编辑器和外部 DOM 保持不变。
- README 增加“销毁可重复调用、宿主节点不会被清空、实例销毁后 API 不可继续使用”的说明。
- 若保留直接挂载到 `options.el` 的兼容模式，必须在初始化前记录并在销毁时恢复原始 children；不建议继续使用 `replaceChildren()` 作为通用清理手段。

### 4.1.5 建议的实现顺序

1. **Runtime 骨架**：新增状态机、清理器注册、节点追踪、异常隔离和幂等测试。
2. **主链路接入**：改造 `XmEditor`、`proxyEditor`，确保 App `unmount` 与 Tiptap `destroy` 顺序正确。
3. **异步资源收口**：接入 Suggestion popup、TOC debounce/highlighter、Table Portal 节点。
4. **组件生命周期审计**：逐个核对 Vue `onMounted/onBeforeUnmount`、Editor `on/off`、DOM `add/removeEventListener`、timer/RAF `set/cancel`。
5. **集成与回归**：补齐多实例、异常初始化、重复销毁和宿主 DOM 保护测试，再更新 README/API 说明。

### 4.1.6 验收标准与测试矩阵

建议引入 Vitest + jsdom（后续再补 Browser/E2E），至少覆盖：

| 场景 | 验收断言 |
| --- | --- |
| 基本销毁 | `vueApp.unmount`、`tiptapEditor.destroy` 各执行一次；Runtime 最终为 `destroyed` |
| 重复销毁 | 连续调用两次及以上不抛错，不重复触发用户 `onDestroy` |
| Proxy/Class 交叉销毁 | 任一入口销毁后另一入口调用无副作用 |
| 活跃 Slash/Emoji 弹层 | `tippy` 实例、popup App、浮层 `el` 均被销毁，`document.body` 无残留节点 |
| TOC 异步任务 | fake timers/RAF flush 后不再触发回调；scroll listener 已移除 |
| Table 边缘按钮 | `table-plus-btn` 节点和 onclick 引用已清理 |
| Vue 组件监听器 | transaction、contextmenu、keydown、scroll、resize 等 `on/off` 配对 |
| 宿主 DOM 保护 | 宿主预置 sentinel 节点和其他实例节点仍存在 |
| 多实例隔离 | 销毁 A 不影响 B 的内容、菜单、监听器和 Portal |
| 初始化异常回滚 | 任一步骤抛错后，已创建的 App、Editor、DOM、timer 均被回收 |
| 长循环稳定性 | 反复创建/销毁 100 次，监听器计数回到基线；浏览器 Heap Snapshot 无持续增长趋势 |

Definition of Done：上述自动化测试全部通过；开发环境无未处理异常；手工检查 DOM、事件监听和定时器无残留；README 与 API 类型/实现保持一致。

### 4.1.7 非目标与后续衔接

- 本 P0 不处理代码主题全局 ID、主题多实例和 CDN 离线问题，这些归入 4.8；但 Runtime 接口需预留实例资源登记能力。
- 本 P0 不改变编辑器内容模型、Extension Manifest 结构和公开菜单行为。
- 完成 Runtime 后，可复用于后续上传管理器、协同连接、AI 流式请求的 AbortController 和资源清理，避免再次出现“功能可用但无法完整回收”的问题。

## 4.2 P0：配置解析和实例隔离存在风险

当前构造器直接读取 `options.config.name`，当 `config` 未传入时会抛出异常。

另外，Preset 合并是浅合并。在用户没有覆盖 Extensions 时，默认扩展数组可能继续被复用；TOC 事件注入逻辑会直接修改 `config.extensions` 中的元素，存在多个编辑器实例共享和污染默认配置的风险。

建议增加不可变的配置规范化流程：

```text
用户配置
  → 参数校验
  → 解析 Preset
  → 深层复制可变配置
  → 合并 Extension
  → 检查重复、依赖和冲突
  → 生成只读 RuntimeConfig
```

同时建议明确：

- `config` 是否必填。
- `extensions` 和 `config.extensions` 同时存在时的优先级。
- 同名扩展的覆盖规则。
- Extension 缺少依赖时的错误行为。
- 一个配置对象能否安全创建多个编辑器实例。

## 4.3 P0：公开配置与实际行为不一致

README 和 Preset 中公开了以下配置：

- `editorOption.contentType`
- `editorOption.debounce`
- 菜单项 `priority`
- 菜单项 `shouldShow`

但当前核心运行逻辑没有完整消费这些配置：

- `contentType` 没有参与内容解析或输出策略。
- `debounce` 没有应用到核心 `onUpdate` 回调。
- 菜单项没有按照 `priority` 排序。
- Fixed/Bubble Menu 没有统一按照 `shouldShow` 过滤菜单项。

建议建立“文档即契约”的 API 测试，所有 README 中公开的配置都必须有自动化测试覆盖。

## 4.4 P0：构建产物体积过大

本次实测构建结果：

| 产物 | 原始体积 | gzip 体积 |
| --- | ---: | ---: |
| `xm-editor.es.js` | 约 4.12 MB | 约 908.76 KB |
| `xm-editor.umd.js` | 约 3.03 MB | 约 755.40 KB |
| Demo JS | 约 3.09 MB | 约 784.40 KB |

Demo 构建已经触发 Vite 的大 Chunk 警告。

主要原因包括：

1. `src/extensions/index.js` 一次性导入所有扩展，消费者难以真正按需加载。
2. CodeBlock 使用 `createLowlight(all)`，打入全部语言定义。
3. 大量 Tiptap/Vue UI 依赖进入最终 Bundle。
4. Collaboration、Yjs 等当前未使用依赖仍存在于 dependencies 中。
5. Table、CodeBlock、Emoji 等重型功能没有独立入口或懒加载机制。

建议目标：

- 基础编辑器 gzip 小于 150 KB。
- NotionLike 完整预设 gzip 小于 350 KB。
- CodeBlock、Table、Collaboration 可以独立加载。
- 构建阶段自动检查包体积预算。

具体措施：

- 增加子路径导出，例如：

```json
{
  "exports": {
    ".": "./dist/index.js",
    "./core": "./dist/core.js",
    "./presets/notion-like": "./dist/presets/notion-like.js",
    "./extensions/image": "./dist/extensions/image.js",
    "./extensions/code-block": "./dist/extensions/code-block.js"
  }
}
```

- 将 Vue、Tiptap 核心依赖整理为 Peer Dependencies。
- Lowlight 改为用户注册语言或默认只注册常用语言。
- 对重型 NodeView 和数据集采用动态导入。
- 检查并移除未使用的生产依赖。

## 4.5 P0：CommonJS 发布入口存在问题

`package.json` 设置了 `"type": "module"`，但将 `dist/xm-editor.umd.js` 声明为 `require` 入口。本次实测 CommonJS `require()` 没有暴露 `XmEditor`、`Extensions` 和 `Presets`。

建议：

- 若继续支持 CommonJS，生成明确的 `.cjs` 文件。
- 若只支持 ESM，则删除误导性的 `require` 条件和 `main` 配置。
- 增加对最终 npm 包的安装冒烟测试，而不是只测试源码构建。

发布验证至少应覆盖：

1. ESM import。
2. CommonJS require，若声明支持。
3. Vite Vue 项目安装和构建。
4. Nuxt/SSR 环境 import。
5. CSS 子路径导入。
6. `npm pack` 后的文件清单和体积。

## 4.6 P0：自动化质量体系缺失

当前项目没有完整的：

- 单元测试。
- Vue 组件测试。
- 浏览器 E2E 测试。
- Lint 和格式检查。
- Type Check。
- 发布工作流。
- Bundle Size 检查。
- API 兼容性检查。

现有 GitHub Actions 主要负责 Demo 部署，无法阻止功能回归进入主分支。

建议测试分层：

| 层级 | 工具建议 | 重点对象 |
| --- | --- | --- |
| 单元测试 | Vitest | Preset 合并、ExtensionManager、Proxy、TOC 工具函数 |
| 组件测试 | Vitest + Vue Test Utils | 菜单状态、弹层、NodeView、上传状态 |

优先覆盖场景：

## 4.7 P1：Vue 集成方式不够自然

当前 `XmEditor` 内部调用 `createApp()`，对于 Vue 组件库会限制：

- `v-model`。
- Provide/Inject。
- Scoped Slots。
- 宿主应用主题上下文。
- SSR/Nuxt。
- Vue 错误边界。
- DevTools 组件树。
- 外部工具栏和状态复用。

建议同时提供声明式组件 API：

```vue
<XmEditor
  v-model="content"
  content-format="json"
  :extensions="extensions"
  :editable="editable"
  @update="handleUpdate"
>
  <template #toolbar="{ editor }">
    <CustomToolbar :editor="editor" />
  </template>

  <template #slash-item="{ item, active }">
    <CustomSlashItem :item="item" :active="active" />
  </template>
</XmEditor>
```

同时增加：

- `useXmEditor()` Composable。
- `useEditorState()`。
- `useEditorCommands()`。
- `useEditorUpload()`。

现有命令式 Class API 可以保留，用于非 Vue 场景和渐进式接入。

## 4.8 P1：主题系统不支持可靠的多实例和离线环境

当前代码主题加载器使用全局固定 DOM ID，并从 CDN 加载 CSS，可能导致：

- 多个编辑器无法使用不同代码主题。
- 一个实例会替换另一个实例的主题。
- 离线、内网或严格 CSP 环境加载失败。
- 仓库中已经复制到产物的本地代码主题没有被实际使用。

建议：

- 代码主题改为静态导入或局部 Class。
- 通过 CSS Variables 定义颜色、间距、圆角、边框、阴影和字体 Token。
- 避免用全局 ID 管理编辑器实例资源。
- 提供 Light、Dark、System 三种模式。
- 允许业务传入完整 Design Tokens。

## 4.9 P1：可访问性和国际化不足

当前多个菜单使用可点击 `div`，缺少完整的：

- Button 语义。
- 键盘焦点。
- `aria-label`。
- `aria-pressed`。
- `role=listbox/option`。
- `aria-selected`。
- 焦点可见样式。
- 减少动画偏好支持。

Slash Menu 的分类名称、空状态和大量 UI 文案直接使用中文常量，也不利于英文或业务自定义。

建议：

- 建立统一的无障碍菜单和按钮基础组件。
- 参考 WAI-ARIA Toolbar、Menu、Listbox 交互模式。
- 提供 `locale` 和 `messages` 配置。
- 内置 `zh-CN`、`en-US`，允许业务覆盖单个文案。
- 建立 Chrome、Firefox、Safari 的最低版本矩阵。

## 6.4 第四阶段：AI 编辑能力

当前分支名为 `feature/new-ai`，但代码中尚未形成完整 AI 能力。建议 AI 扩展保持 Provider-Neutral，不直接绑定单一服务。

### 推荐能力

- 续写。
- 改写。
- 扩写和缩写。
- 翻译。
- 总结。
- 调整语气。
- 根据选区生成标题、列表或表格。
- `/ai` Slash 命令。
- 选区 Bubble AI 菜单。
- 流式插入和停止生成。
- 一键撤销本次生成。
- 自定义 Prompt。
- 业务知识上下文注入。
- 大文档按选区、标题或块构建上下文。

### 推荐交互原则

- AI 输出先预览，再接受或拒绝。
- 不直接覆盖用户原文。
- 每次 AI 修改作为一个可撤销 Transaction。
- 明确生成中、失败、取消和重试状态。
- API Key 通过业务服务端代理，编辑器前端不保存密钥。
- AI Provider 只负责流和结果，编辑器负责选区、Transaction 和 UI。

建议接口：

```ts
interface AIProvider {
  stream(request: AIRequest, signal: AbortSignal): AsyncIterable<AIChunk>
}

interface AIRequest {
  action: string
  selectedText?: string
  documentContext?: unknown
  prompt?: string
  locale?: string
}
```

## 9. 工程治理建议

### 推荐脚本

```json
{
  "scripts": {

    "typecheck": "vue-tsc --noEmit",
```

## 10. 最终建议

XmEditor 当前最有价值的部分不是扩展数量，而是已经形成了“扩展逻辑 + 菜单 Manifest + Vue UI + Preset”的完整构建思路。

后续工作的核心应从“继续增加功能”转向以下四点：

1. **可靠性**：生命周期、配置隔离、内容 Schema 和测试。
2. **开发者体验**：TypeScript、Vue 声明式 API、Slots 和文档契约。
3. **交付质量**：按需加载、包体积、发布验证和浏览器兼容。
4. **产品差异化**：中文体验、协同审阅和可替换 AI Provider。

完成 P0 和 P1 后，项目才会从“功能丰富的个人开源项目”进入“团队可以放心依赖的编辑器基础设施”。
