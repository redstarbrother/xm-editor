# XmEditor 4.2、4.3 章节修复方案

> 对应文档：`doc/项目分析及后续开发规划.md` 4.2、4.3
>
> 目标版本：建议作为下一个 P0 质量版本完成，不与协同、AI 等新功能混合发布。

## 1. 修复范围

本方案处理两类相互关联的问题：

1. **4.2 配置解析和实例隔离**：保证缺省配置、Preset、扩展覆盖和 TOC 事件注入经过统一解析；同一个配置对象可以安全创建多个编辑器实例。
2. **4.3 公开配置与实际行为**：让 `contentType`、`debounce`、菜单 `priority` 和 `shouldShow` 真正参与运行时行为，并用自动化测试固定 API 契约。

本方案不改变 Tiptap 文档模型，不移除现有 Class/Proxy API，也不处理 Runtime 销毁、包体积和主题加载等其他章节的问题。4.2 的配置规范化层应与 4.1 的 `EditorRuntime` 对接，但不依赖 Runtime 的具体实现。

## 2. 当前实现与问题边界

### 2.1 配置链路

当前链路大致为：

```text
new XmEditor(options)
  -> options.config || {}
  -> 若存在 name/configure，则执行 configure()
  -> 直接读取 config.editorOption/config.extensions/config.events
  -> ExtensionManager(options.extensions || config.extensions || [])
```

已确认的风险：

- `options.extensions` 与 `config.extensions` 是两条入口。ExtensionManager 使用前者优先，但 `injectTocEvent()` 只读取后者，可能导致 TOC 事件注入到未实际使用的数组。
- `mergePresetConfig()` 只复制 `editorOption`、`style`、`events` 的第一层；默认 `extensions` 数组及其中的扩展 Manifest/配置对象仍可能被多个实例共享。
- `injectTocEvent()` 通过 `extensions[tocIndex] = tocExt.configure(...)` 改写传入数组。用户重复调用同一个 `configure()` 结果或复用同一个配置对象时，实例之间可能互相污染。
- 当前代码虽然用 `options.config || {}` 避免了完全缺省时的直接异常，但没有对 `config` 类型、Preset 形态和字段值进行统一校验。传入 `null`、错误的 Preset 对象或错误类型字段时，错误位置不稳定。
- 扩展名称重复、扩展缺少 `name`、同名覆盖和依赖缺失没有明确规则，错误可能延迟到 Tiptap 初始化阶段。

### 2.2 公开配置链路

- `editorOption.contentType` 出现在 Preset 和 README 中，但初始化内容直接传给 Tiptap，`onUpdate` 也没有根据它生成内容结果。
- `editorOption.debounce` 出现在 Preset 和 README 中，但 `XmEditor.initTiptapEditor()` 直接同步调用 `events.onUpdate`。
- 菜单项普遍使用 `order`，`ExtensionManager.getFixedMenuItems()` 和 `getBubbleMenuItems()` 只做收集，不排序。
- 菜单项可以声明 `shouldShow`，但 Fixed Menu 直接渲染全部条目，Bubble Menu 也没有对每个条目统一过滤；`shouldShow` 目前只被部分上层显示逻辑间接使用。
- 菜单回调没有统一的异常边界。某个 `shouldShow` 抛错时，可能影响整组菜单的计算。

## 3. 目标配置契约

### 3.1 输入配置形态

支持以下三种明确形态：

```js
// 直接配置
new XmEditor({ el, config: { editorOption, extensions, events, style } })

// Preset 配置结果
new XmEditor({ el, config: Presets.NotionLike.configure(userConfig) })

// Preset 本身，由 XmEditor 负责调用 configure
new XmEditor({ el, config: Presets.NotionLike })
```

`config` 可省略，等价于空配置；`options` 必须是对象。若 `config` 既不是配置对象，也不是包含 `name` 和 `configure()` 的 Preset，则在初始化早期抛出 `XmEditorConfigError`，错误信息包含字段路径和修复建议。

### 3.2 入口优先级

统一定义为：

1. `options.extensions`：实例级显式扩展列表，优先级最高。
2. `config.extensions`：配置级扩展列表。
3. Preset 默认扩展列表：仅在前两者都未提供时使用。

为避免“空数组到底是未提供还是明确禁用”的歧义，建议采用以下规则：

- 字段未定义：继续使用下一级默认值。
- 明确传入 `extensions: []`：表示使用空扩展列表，不自动补回 Preset 默认扩展。
- `options.extensions` 与 `config.extensions` 同时存在：使用 `options.extensions`，开发环境给出一次 warning。

### 3.3 同名扩展覆盖规则

将扩展列表按 `name` 规范化：

- 有效扩展必须是对象并包含非空字符串 `name`。
- 同名扩展采用“后者覆盖前者，但保留前者位置”的规则；`options.extensions` 覆盖 `config.extensions`，用户扩展覆盖 Preset 默认扩展。
- 没有 `name` 的扩展直接报错，不再静默丢弃。
- 同名扩展重复声明时开发环境 warning；最终配置只保留一个实例。
- `extension`、`manifest`、`component` 等字段均属于扩展描述的一部分，覆盖时整体替换，避免把两个扩展的菜单和编辑逻辑错误拼接。

### 3.4 配置不可变性

规范化过程必须创建新的配置图，不修改调用方对象和 Preset 默认对象。复制边界如下：

- `editorOption`、`style`、`events`、`extensions` 数组复制。
- 每个扩展描述对象复制。
- `manifest`、`fixedMenu`、`bubbleMenu`、`slashMenu`、`suggestion` 等可变配置对象和数组递归复制。
- 函数、Vue 组件、Tiptap Extension 实例和用户自定义 opaque 值保持引用；绝不通过 JSON 序列化复制，以免丢失函数和组件。

建议新增 `cloneConfigValue()`，只复制 plain object 和 array；对扩展实例及组件使用引用保留策略。规范化完成后可在开发环境冻结配置（`Object.freeze` 递归冻结），生产环境不强制冻结以降低开销。

## 4. 目标 API 行为

### 4.1 `contentType`

支持 `json` 和 `html`，默认值为 `json`。规范化时校验值，不支持的值抛出配置错误。

| `contentType` | 初始 `content` | `onUpdate` 新增字段 `content` | 代理读取建议 |
| --- | --- | --- | --- |
| `json` | JSON 文档对象；也可接受合法 JSON 字符串 | `editor.getJSON()` | 保持 `getJSON()`，新增 `getContent()` 返回 JSON |
| `html` | HTML 字符串 | `editor.getHTML()` | 保持 `getHTML()`，新增 `getContent()` 返回 HTML |

兼容约束：`onUpdate` 继续传递原有 `{ editor }`，只新增 `{ content, contentType }`，不要求现有业务改写。`setContent()` 继续接受 Tiptap 支持的对象或字符串；如传入 JSON 字符串，在 `contentType: 'json'` 下先解析并对非法 JSON 给出明确错误。

建议抽出 `src/core/contentAdapter.js`：

```js
normalizeContent(content, contentType)  // 校验/解析初始内容
serializeContent(editor, contentType)   // 生成事件和 getContent() 的结果
assertContentType(contentType)
```

`normalizeContent()` 不负责把 HTML 转成 JSON 或反向转换，Tiptap 负责解析对应格式；它只负责类型校验、JSON 字符串解析和错误信息。

### 4.2 `debounce`

`editorOption.debounce` 只控制 `events.onUpdate`，不延迟 Tiptap transaction、菜单状态、TOC 或用户直接读取编辑器内容。规则如下：

- 默认 `300ms`，`0` 表示同步触发。
- 必须是大于等于 0 的有限数字，否则抛出配置错误。
- 每次更新只保留最新一次回调参数。
- `onFocus`、`onBlur`、`onInit`、`onDestroy` 不受该配置影响。
- 销毁时取消待执行的 update timer；默认不在销毁阶段补发一次 `onUpdate`。

建议新增通用 `createDebouncedCallback(fn, delay)`，提供 `cancel()` 和 `flush()`；在 `XmEditor` 初始化时创建，在 Runtime 清理阶段登记 `cancel()`。开发环境可在回调抛错时通过统一错误处理上报，不能吞掉业务错误。

### 4.3 菜单 `priority`

菜单项支持 `priority`，并保留现有 `order` 作为兼容别名：

- `priority` 优先于 `order`。
- 未设置时按 `0` 处理。
- 数值越小越靠前，保持现有 `order: 10/20/30...` 的工具栏顺序。
- priority 相同保持扩展声明顺序，保证排序稳定。
- `type: 'separator'` 参与同一排序，随后进行首尾和相邻无效分隔符清理。

`ExtensionManager` 负责返回已经排序的菜单数据，不把排序逻辑散落到 Vue 组件中。返回给组件的条目可补充只读字段 `resolvedPriority`，便于调试，但不修改用户对象。

### 4.4 菜单 `shouldShow`

Fixed/Bubble Menu 统一使用同一套可见性计算：

```js
shouldShow?.({ editor, state, view }) !== false
```

- 未声明 `shouldShow` 的条目默认可见。
- 回调返回 `false` 时隐藏；返回其他值按可见处理。
- 回调抛错时记录一次错误并隐藏该条目，不能阻断其他菜单。
- 计算应在 editor 的 `transaction` 事件后刷新，在菜单条目变化时重新计算。
- Fixed Menu 过滤后再清理无效 separator；Bubble Menu 也必须执行相同过滤。
- 菜单点击前再次检查 `shouldShow`，避免状态已变化时执行不可用命令。

新增 `src/core/menuConfig.js` 或同等纯函数模块，提供 `resolveMenuItems()`、`filterVisibleMenuItems()`、`cleanupSeparators()`，让排序、过滤和异常处理可以脱离 Vue 单元测试。

## 5. 建议代码改动

### 5.1 新增配置规范化模块

新增 `src/core/config/normalizeConfig.js`（目录名称可按项目现有风格调整），建议导出：

```js
normalizeEditorConfig(options)
normalizePresetConfig(preset, userConfig)
normalizeExtensions({ preset, config, explicit })
validateEditorOption(editorOption)
```

返回只供当前实例使用的 `runtimeConfig`：

```js
{
  editorOption: {
    editable, autofocus, content, contentType, debounce, placeholder, ...
  },
  extensions: [],
  events: {},
  style: {},
  meta: { presetName, warnings: [] }
}
```

`XmEditor` 构造器只负责调用一次规范化模块，然后把同一个 `runtimeConfig` 传给 `injectTocEvent()`、`ExtensionManager`、Tiptap 初始化和 Vue View，避免各模块各自解释原始 options。

### 5.2 重写 Preset 合并

将 `src/utils/presetUtil.js` 的 `mergePresetConfig()` 改为不可变合并：

1. 先复制 Preset 默认配置。
2. 合并 `editorOption`、`style`、`events`。
3. 按名称合并扩展，保留默认位置并追加新扩展。
4. 对扩展描述内的菜单和 suggestion 配置做递归复制。
5. 不把空数组误判为“没有覆盖”。

`configure(userConfig = {})` 每次调用都必须返回新的对象；增加测试证明：连续调用两次的结果互不影响，修改第一次结果不会改变 `defaultConfig` 或第二次结果。

### 5.3 调整 `XmEditor` 初始化顺序

建议顺序：

```text
校验 options
  -> normalizeEditorConfig(options)
  -> 创建 ExtensionManager(runtimeConfig.extensions, ...)
  -> 将 TOC 事件注入规范化后的扩展副本
  -> 创建 Tiptap Editor
  -> 创建 Vue UI
  -> 创建 Proxy
```

TOC 注入必须返回新扩展描述或新扩展实例，不直接修改 `runtimeConfig.extensions` 之外的对象。`options.extensions` 和 `config.extensions` 经过规范化后只保留一条实际使用链路。

### 5.4 接入内容适配和更新防抖

在 `initTiptapEditor()` 中：

- 用 `normalizeContent()` 处理初始内容。
- 用 `serializeContent()` 生成 `onUpdate` 的 `content`。
- 用防抖包装器调用 `events.onUpdate`。
- 把取消函数登记到 `EditorRuntime`，保证异常初始化和销毁都能清理。

Proxy 中新增 `getContent()` 和 `getContentType()`；旧有 `getHTML()`、`getJSON()` 保持不变。

### 5.5 统一菜单解析

调整 `ExtensionManager.getFixedMenuItems()`、`getBubbleMenuItems()`：

- 复制 manifest，不修改原对象。
- 解析 `priority ?? order ?? 0`。
- 进行稳定排序。
- 返回给 Vue 的列表带上原始 `shouldShow`，由统一的可见性 Composable 计算。

新增 `useMenuVisibility(editor, items)`，监听 `transaction`，返回响应式可见列表。FixedMenu 和 BubbleMenu 都使用它；两者不再各自实现过滤规则。

## 6. 兼容性策略

- `config` 缺省仍可创建编辑器，行为等价于空配置；如果没有 `el`，保留当前警告行为，但配置校验仍然先执行。
- 保留 `order`，并将其作为 `priority` 的兼容别名；现有内置菜单的显示顺序不变。
- 保留 `onUpdate({ editor })` 的参数；`content` 和 `contentType` 为新增字段。
- `getHTML()`、`getJSON()`、`setContent()` 行为不删除；新增 `getContent()` 不强制业务迁移。
- 已有 `Presets.*.configure()` 调用方式不变；只改变其返回值不再共享默认扩展对象。
- 对无效配置采用开发环境 warning + 明确异常的策略：影响数据正确性的字段（如 contentType、debounce、无 name 扩展）直接抛错；可兼容字段（如 order）只 warning。

## 7. 测试方案

建议引入 Vitest；纯函数优先，不依赖浏览器。测试文件可放在 `tests/unit/`。

### 7.1 4.2 配置和隔离测试

| 场景 | 断言 |
| --- | --- |
| 无 `config` | 不抛异常，得到默认空配置 |
| `config: null`/错误类型 | 抛出 `XmEditorConfigError`，包含字段路径 |
| 传入 Preset 本身 | 只调用一次 `configure()`，使用返回的新对象 |
| `options.extensions` 优先 | ExtensionManager 与 TOC 注入使用同一最终数组 |
| 明确 `extensions: []` | 不自动补回 Preset 扩展 |
| 同名覆盖 | 后者覆盖前者，位置稳定，只保留一个扩展 |
| 缺少 name | 初始化前失败，错误指向扩展索引 |
| 两次 configure | 修改实例 A 的扩展/菜单配置不影响实例 B 和 defaultConfig |
| TOC 事件注入 | 注入不修改用户传入数组和原始扩展对象 |
| 三个实例并存 | 每个实例的 extension、events、菜单配置互不影响 |

### 7.2 4.3 行为契约测试

| 场景 | 断言 |
| --- | --- |
| `contentType: json` | 初始 JSON 对象可加载，update 的 `content` 等于 `getJSON()` |
| `contentType: html` | 初始 HTML 可加载，update 的 `content` 等于 `getHTML()` |
| 非法 contentType | 初始化前抛出配置错误 |
| JSON 字符串内容 | 合法字符串被解析，非法字符串给出明确错误 |
| `debounce: 0` | 每次 update 同步触发一次 |
| `debounce: 100` | 100ms 内多次更新只触发最后一次 |
| debounce 销毁 | 销毁后待执行回调不会触发 |
| priority | `priority` 优先于 `order`，数值小者在前，相同值保持稳定 |
| shouldShow 缺省 | 条目可见 |
| shouldShow 返回 false | Fixed/Bubble 均隐藏该条目 |
| shouldShow 状态变化 | transaction 后列表正确刷新 |
| shouldShow 抛错 | 仅隐藏该条目，其余条目正常显示并记录错误 |
| 分隔符清理 | 过滤后首尾及连续无效 separator 不渲染 |
| 点击时二次检查 | 已不可见的条目不执行 action |

### 7.3 手工回归

至少在 Demo 中检查：NotionLike、Basic、Comment 三个 Preset；两个相同 Preset 实例同时存在；一个实例配置 HTML、另一个配置 JSON；选区变化时 Bubble Menu；空选区和不可执行命令下 Fixed Menu；中文输入法组合输入期间不触发异常。

## 8. 实施顺序与验收标准

### 阶段一：配置收口

1. 新增错误类型、plain object 复制器和配置规范化函数。
2. 重写 Preset 合并和扩展按名称合并逻辑。
3. 调整 `XmEditor` 使用单一 `runtimeConfig`，修复 TOC 注入路径。
4. 完成 4.2 单元测试。

阶段验收：默认配置、Preset 配置和显式扩展三条入口的实际 ExtensionManager 输入一致；重复创建实例不会改变任何共享对象。

### 阶段二：内容和事件契约

1. 新增 content adapter。
2. 接入 `contentType` 和 `getContent()`。
3. 接入 `debounce`、cancel 和 Runtime 清理。
4. 更新中英文 README 的配置和事件示例。

阶段验收：JSON/HTML 两种模式的初始内容、update payload 和代理读取结果一致；销毁后没有延迟 update 回调。

### 阶段三：菜单契约

1. 新增菜单排序、过滤和 separator 清理纯函数。
2. 改造 ExtensionManager、FixedMenu、BubbleMenu。
3. 增加 transaction 驱动的可见性更新和点击前检查。
4. 完成菜单契约测试和 Demo 回归。

阶段验收：所有菜单实现统一的 priority/shouldShow 规则，现有 order 顺序不发生意外变化。

### Definition of Done

- 4.2、4.3 测试全部通过，且新增测试不依赖真实网络或时间不稳定行为。
- README 中文和英文版本与实际参数、默认值、事件 payload 一致。
- `npm run build` 成功，三套 Preset 可在 Demo 中启动。
- 开发环境不存在由配置共享、无效菜单回调或延迟 update 引起的未处理异常。
- 代码审查确认原始用户配置、Preset 默认配置和其他编辑器实例均不会被当前实例改写。

## 9. 风险与后续事项

- `contentType` 的输出字段是新增契约，业务若只读取 `editor` 不受影响；业务若自行假设 update 只同步触发，需要根据 `debounce` 明确调整。
- Fixed Menu 应用 `shouldShow` 后，部分现有内置按钮会在不可执行时隐藏；这是公开配置语义的落地，需要在 Demo 中确认是否需要为某些菜单移除过于严格的内置条件。
- 复制扩展描述不能复制 Tiptap Extension 实例本身；若第三方扩展在 `configure()` 内部修改自身实例，应在扩展开发规范中要求返回新实例。
- 本方案只规定运行时配置契约，不引入 TypeScript；后续可基于 `runtimeConfig` 和菜单 Manifest 补充类型声明与 API 兼容检查。
